## Топ-50 вопросов
### Мои ответы на Блок5 (диагностика)
#### 1. SQL-инъекция
- «должен ли QA это знать? искать уязвимости? SQL-инъекция это вставка SQL-кода в поле ввода. как проверить не помню»

✅ Определение верное. Проверка:
- «Ввести в поле ввода (логин, поиск) строку ' OR '1'='1 или '; DROP TABLE users; --. Если приложение пускает без пароля или падает — уязвимо. В нашем полигоне я проверяла это в TC-10 (' OR '1'='1).»
- QA должен это знать, потому что ты проверяешь безопасность как часть тестирования.

#### 2. XSS
- «должен ли QA это знать? искать уязвимости? XSS это вставка JavaScript в страницу. как проверить не помню»

✅ Определение верное. Проверка:
- «Ввести в поле <script>alert(1)</script>. Если появилось всплывающее окно — уязвимо. В полигоне я проверяла в TC-11.»
- QA должен это знать, потому что XSS — частая уязвимость.

#### 3. JWT
- «JWT это способ передать инфо о пользователе в виде подписанного токена. Нужен для авторизации.»

✅ Верно! Можно добавить: 
- «Токен передаётся в заголовке Authorization: Bearer <токен> и проверяется на сервере.»

#### 4. Авторизация и аутентификация
- «Авторизация — это права в системе. Аутентификация — это логин и пароль.»

✅ Верно. Уточнение:
- Аутентификация — «кто ты?» (логин/пароль).
- Авторизация — «что тебе можно?» (права доступа).

#### 5. Статус-коды
- «200 — ок. 401 — не авторизован, 403 — нет доступа, 404 — не существует, 500 — сервер упал.»

✅ Верно! Ты правильно разложила коды.

#### 6. Чем 401 отличается от 403
Твой ответ: «отличается ограниченным доступом к ресурсу. Не хватает прав.»

✅ Верно, но неполно. Уточнение:
- 401 Unauthorized — «ты не авторизован» (не залогинен, нет токена).
- 403 Forbidden — «ты авторизован, но тебе нельзя» (нет прав).

Пример из полигона:
- без токена /users → 401. С токеном, но без прав на чужие данные → 403.

####7. IDOR
- «не знаю»

⚠️ Пробел. IDOR (Insecure Direct Object Reference) — уязвимость, когда пользователь может получить чужие данные, изменив ID в запросе.

Пример:
- GET /users/1 (свой профиль), а ты меняешь на GET /users/2 — и видишь чужой профиль. Это IDOR.

В полигоне: 
- BUG-07 (все пользователи видны любому авторизованному) — это частный случай IDOR.

#### 8. Как проверить, что API защищён
- «отправить апи запрос через курл и посмотреть на ответ, если в ответе открытая информация (данные пользователей, пароль) — не защищён. Если информация не пришла в открытом виде — защищён.»

✅ Верно, но поверхностно. 

Проверка:
- Без токена → 401.
- С токеном → 200, но без паролей.
- С токеном другого пользователя → не видит чужие данные (IDOR).
- Пароли в БД — в виде хеша (bcrypt).

#### 9. HTTPS
- «это защищенный протокол»

✅ Верно. Можно добавить: 
- «HTTPS шифрует трафик между браузером и сервером (SSL/TLS).»

#### 10. CORS
- «не знаю»

⚠️ Пробел. 
- CORS (Cross-Origin Resource Sharing) — механизм, который разрешает или запрещает браузеру делать запросы к API с другого домена.

Пример: 
- если сайт http://10.191.30.52 делает запрос к http://10.191.30.50:3000, браузер проверяет, разрешено ли это (CORS). Если нет — блокирует.

### Запомни:
- IDOR — доступ к чужим данным через изменение ID.
- CORS — механизм, разрешающий/запрещающий запросы с других доменов.

### Безопасность (закрываем пробелы)

#### IDOR
- Уязвимость: доступ к чужим данным через изменение ID
- Пример: /users/1 → /users/2
- Проверка: залогиниться, поменять ID, посмотреть, видны ли чужие данные
- В полигоне: BUG-07 (все пользователи видны)

#### CORS
- Механизм, разрешающий/запрещающий запросы с других доменов
- Проверка: заголовок Access-Control-Allow-Origin в ответе API
- Если `*` — небезопасно

#### SQL-инъекция
- Вставка SQL-кода в поле ввода
- Проверка: ' OR '1'='1
- В полигоне: TC-10
- Защита: параметризованные запросы

#### XSS
- Вставка JavaScript в страницу
- Проверка: <script>alert(1)</script>
- В полигоне: TC-11
- Защита: экранирование HTML

### Ответ на вопрос
- QA должен уметь проверять базовые уязвимости (SQL, XSS, IDOR, CORS)
- Но не обязан быть хакером
