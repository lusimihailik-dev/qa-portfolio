📘 День 1 — LXD и первый контейнер
1. Что такое LXD и зачем он QA
LXD — это менеджер контейнеров (система контейнеризации) в Ubuntu. Он позволяет запускать изолированные мини-системы (контейнеры) внутри твоей основной ОС.

Чем контейнер отличается от виртуальной машины (VM):

Контейнер (LXD)	Виртуальная машина
Ядро	Использует ядро хоста	Своё ядро
Размер	~100–500 МБ	~1–2 ГБ
Запуск	Секунды	Минуты
Изоляция	На уровне ОС	Полная (аппаратная)
Для QA	Идеально для быстрых песочниц	Тяжело, медленно
Зачем QA контейнер:

Песочница — можно ломать, ставить, удалять, не боясь сломать основную систему.

Тестовый стенд — можно поднять сайт, API, БД в отдельных контейнерах.

Изоляция — каждый сервис в своём контейнере, как в реальной работе.

Быстро — создать/удалить контейнер — секунды.

2. Установка и проверка LXD
bash
lxc --version          # проверить версию
lxc remote list        # список репозиториев образов
lxc image list ubuntu: # образы Ubuntu (контейнерные)
Важно: lxc — это клиент. Есть ещё lxd — демон (сервис). Команды управления — через lxc.

3. Создание и управление контейнером
bash
lxc launch ubuntu:22.04 qa-base    # создать и запустить контейнер qa-base
lxc list                            # список контейнеров и их статус
lxc info qa-base                    # подробная информация
lxc start qa-base                   # запустить остановленный
lxc stop qa-base                    # остановить
lxc delete qa-base                  # удалить
Разбор lxc launch:

ubuntu:22.04 — образ (репозиторий ubuntu, версия 22.04)

qa-base — имя контейнера

4. Работа внутри контейнера
bash
lxc exec qa-base bash              # зайти как root
lxc exec qa-base -- su - mila      # зайти как пользователь mila
lxc exec qa-base -- ls /home       # выполнить одну команду
Важно: внутри контейнера ты работаешь как в обычной Ubuntu. Все команды Linux (День 2) применимы.

Выход из контейнера:

bash
exit
5. Передача файлов между хостом и контейнером
bash
lxc file pull qa-base/home/mila/file.txt ~/file.txt   # из контейнера на хост
lxc file push ~/file.txt qa-base/home/mila/file.txt   # с хоста в контейнер
6. Группа lxd и права доступа
Проблема: после установки LXD обычный пользователь не может управлять контейнерами — permission denied.

Решение:

bash
sudo usermod -aG lxd mila    # добавить в группу
newgrp lxd                   # подхватить в текущем терминале
groups                       # проверить
Важно: изменение групп применяется только к новым сессиям входа. Закрытие/открытие терминала — не считается. Нужен полный Log Out / Log In или перезагрузка.

Проверка:

bash
id               # группы текущей сессии
id mila          # группы в системе (файл /etc/group)
Может быть расхождение: в системе группа есть, в текущей сессии — нет. Это классический баг/вопрос на собеседовании.

7. Итог Дня 1
Команда	Что делает

lxc list	Список контейнеров
lxc exec qa-base bash	Зайти внутрь
lxc file pull/push	Передача файлов
newgrp lxd	Подхватить группу
Что создано: контейнер qa-base (Ubuntu 22.04) — будущая песочница для практики.

3. Права доступа
Три группы прав: владелец / группа / остальные.

Числа: r=4, w=2, x=1.

Число	Символы	Смысл
755	rwxr-xr-x	Стандарт для папок
644	rw-r--r--	Стандарт для файлов
600	rw-------	Только владелец
775	rwxrwxr-x	Владелец и группа всё могут
Команды:

bash
chmod 755 file.txt     # изменить права
chown mila:mila file   # сменить владельца и группу
ls -l file.txt         # проверить права
Важно: x на папке = «можно войти внутрь». Без x не сможешь даже cd.

Эксперимент: создали файл с 600, другой юзер tester не смог прочитать → Permission denied. Root обходит права.

📘 День 3 — Git: контроль версий
1. Что такое Git и зачем QA
Git — система контроля версий. Хранит историю изменений файлов, позволяет откатываться, работать в команде.

Зачем QA:

Работа в репозитории с командой.

Тест-кейсы, чек-листы, баг-репорты можно вести в Git.

Портфолио на GitHub — обязательный пункт резюме.

На собеседовании спросят: «что такое commit, branch, pull request».

2. Что такое коммит (главное понятие)
Коммит — это «снимок» состояния файлов в определённый момент. У каждого коммита есть:

Хеш — уникальный ID (например, a1b2c3d).

Автор — кто сделал.

Дата — когда.

Сообщение — что сделано.

Аналогия: сохранение в игре. Можно вернуться к любой точке.

Коммит = локально. Push = отправить на сервер (GitHub). Pull = забрать с сервера.

3. Три состояния файла в Git
text
Рабочая папка → Индекс → Репозиторий
             git add   git commit
Состояние	Что значит
Untracked	Git не следит за файлом
Modified	Изменён, но не в индексе
Staged	В индексе, готов к коммиту
Committed	Зафиксирован в истории
4. Основные команды
Команда	Что делает
git init	Создать репозиторий
git status	Состояние файлов
git add файл	В индекс
git add .	Все изменения в папке
git add -A	Все, включая удаления
git commit -m "..."	Зафиксировать
git log --oneline	История кратко
git diff	Что изменилось
git diff HEAD~1 HEAD	Между коммитами
git config --global user.name/email	Настройка
5. Отмена изменений
Ситуация	Команда
Изменила файл, не добавляла в индекс	git restore file
Добавила в индекс, передумала	git restore --staged file
Отменить последний коммит	git reset HEAD~1
Отменить коммит и изменения	git reset --hard HEAD~1 (опасно!)
Правило: git restore и git reset --hard не спрашивают подтверждения. Корзины нет.

6. Понятия
Термин	Что значит
Репозиторий	Папка под контролем Git (есть .git)
Индекс (staging)	Что войдёт в следующий коммит
Commit	Снимок состояния
HEAD	Указатель на текущий коммит
7. Ловушки
Git работает только внутри папки с .git. Если нет — fatal: not a git repository.

~/файл — попытка выполнить файл, а не открыть. Для просмотра — cat, less, nano.

Для выполнения файла нужен x в правах.

+ в терминале — не «и», а имя файла. Для соединения команд: ;, &&, ||, |.

📘 День 4 — Теория QA: виды и уровни тестирования
1. QA vs QC vs Testing
Термин	Что значит	Аналогия
QA (Quality Assurance)	Обеспечение качества — процессы, предотвращающие баги	Строим дорогу так, чтобы аварий не было
QC (Quality Control)	Контроль качества — проверка продукта	Проверяем готовую дорогу
Testing	Тестирование — конкретные действия по поиску багов	Едем по дороге и ищем ямы
QA-инженер занимается всем, но Junior Manual QA — в основном Testing.

2. Функциональное vs нефункциональное
Функциональное — что система делает.

Логин пускает с правильным паролем.

Корзина считает сумму.

Поиск находит товар.

Нефункциональное — как система это делает.

Скорость загрузки (производительность).

Держит 1000 пользователей (нагрузка).

SSL-сертификат (безопасность).

Работает в Chrome/Firefox (совместимость).

Удобно (юзабилити).

3. Уровни тестирования (пирамида)
Уровень	Кто делает	Что проверяет
Модульное (Unit)	Разработчик	Отдельная функция
Интеграционное	Разработчик/QA	Модули вместе
Системное	QA	Вся система
Приёмочное	Заказчик/QA	Соответствие бизнесу
Пример на qa-base:

Модульное: chmod 600 test.txt → права стали rw-------.

Интеграционное: git add + git commit → появился коммит.

Системное: apt install curl → curl -I URL → статус 200.

4. Виды тестирования
Вид	Что делает
Дымовое (Smoke)	Быстрая проверка основного: сайт открывается, логин работает
Регрессионное	Новое не сломало старое
Санитарное (Sanity)	Узкая проверка конкретного фикса
Исследовательское	Без тест-кейсов, «играем»
Приёмочное	Перед релизом
Позитивное	Правильные данные → всё работает
Негативное	Неправильные данные → система не ломается
5. Ящики
Ящик	Что знаем	Кто
Чёрный	Ничего о внутренностях	QA
Белый	Знаем код	Разработчик
Серый	Частично	Опытный QA
6. SQL-инъекция и XSS
SQL-инъекция — вставка SQL-кода в поле ввода.

Пример: ' OR '1'='1 → вход без пароля.

Опасность: кража данных, удаление таблиц.

Тест: ' OR '1'='1, '; DROP TABLE users; --

Защита: параметризованные запросы, экранирование.

XSS — вставка JavaScript в страницу.

Пример: <script>alert(1)</script> в комментарии.

Опасность: кража cookies, сессий.

Виды: хранимая, отражённая, DOM-based.

Тест: <script>alert(1)</script>, <img src=x onerror=alert(1)>

Защита: экранирование HTML, CSP, HttpOnly cookies.

7. Тестирование сценариев с почтой
Нельзя использовать реальную почту.

Используют Mailtrap.io, temp-mail.org, MailHog.

Проверяют: тему, отправителя, текст, ссылку, срок действия.

Ссылка должна быть одноразовой.

Нельзя раскрывать, что email не найден (утечка информации).

TC-03 «Сброс пароля» — интеграционное тестирование: сайт + почтовый сервер + почтовый ящик.

📘 День 7 — Безопасность API
1. BUG-03: пароли в открытом виде
Проблема: API возвращал пароли в JSON.

Опасность:

При утечке БД все пароли скомпрометированы.

Пароли видны в логах, кэше, DevTools.

Исправление:

Установили bcrypt.

Пароли в БД — в виде хеша.

API не возвращает пароль.

Логин: bcrypt.checkpw.

Проверка:

📘 День 8 — Баг-трекер Redmine (развёрнутый конспект)
1. Зачем QA баг-трекер
В реальной работе багов много. Если их не фиксировать, они теряются, забываются, остаются без исправления.

Баг-трекер решает три задачи:

Задача	Что даёт
Фиксация	Все баги в одном месте, с описанием, шагами, приоритетом
Прозрачность	Команда видит: что сломано, кто отвечает, когда исправят
Workflow	Баг движется по статусам: Новая → В работе → Решена → Закрыта
QA без баг-трекера — как врач без карты пациента. Ты находишь проблему, но не можешь её отследить.

2. Что такое Redmine
Redmine — open-source веб-приложение для управления проектами и баг-трекинга.

Ключевые понятия:

Понятие	Что значит
Проект	Группа задач (например, «QA Polygon»)
Трекер	Тип задачи: Bug (ошибка), Feature (новая функция), Support
Статус	Где сейчас баг: Новая, В работе, Решена, Закрыта, Отклонена
Приоритет	Насколько срочно: Низкий, Обычный, Высокий, Срочный
Назначена	Кто отвечает за исправление
Workflow	Правила переходов между статусами
Почему Redmine, а не Jira: Jira — платная, Redmine — бесплатный и открытый. В учебных целях идеален.

3. Установка Redmine в контейнере
3.1. Создание контейнера
bash
lxc launch ubuntu:22.04 redmine
lxc list redmine
Запомни IP — понадобится для доступа из браузера.

3.2. Установка зависимостей
bash
lxc exec redmine bash
apt update
apt install -y ruby ruby-dev build-essential libxml2-dev libxslt1-dev libpq-dev libffi-dev libjpeg-dev libpng-dev zlib1g-dev libssl-dev libyaml-dev libreadline-dev libgdbm-dev libncurses-dev bison libbison-dev imagemagick libmagickwand-dev git postgresql postgresql-contrib
Что ставим:

ruby, ruby-dev — язык Redmine

libpq-dev — для PostgreSQL

imagemagick — обработка изображений (аватарки, вложения)

postgresql — база данных

3.3. Настройка PostgreSQL
bash
systemctl start postgresql
sudo -u postgres createuser -P redmine   # пароль: redmine_password
sudo -u postgres createdb -O redmine redmine
Проверка: sudo -u postgres psql -l → видим redmine.

3.4. Скачивание Redmine
Официальный сайт redmine.org может быть недоступен из России. Используем GitHub:

bash
cd /opt
git clone https://github.com/redmine/redmine.git -b 5.1-stable
mv redmine redmine-src
cd /opt/redmine-src
3.5. Настройка database.yml
bash
cp config/database.yml.example config/database.yml
nano config/database.yml
Секция production: должна быть:

yaml
production:
  adapter: postgresql
  database: redmine
  host: localhost
  username: redmine
  password: "redmine_password"
  encoding: utf8
  schema_search_path: public
Важно: удали блок variables: с transaction_isolation: "READ-COMMITTED" — это настройка для MySQL, PostgreSQL её не принимает.

3.6. Установка зависимостей
bash
gem install bundler
bundle config set --local without 'development test'
bundle install
Проблема: Redmine пытается поставить mysql2, даже если нужен только PostgreSQL.
Решение: apt install -y libmariadb-dev или bundle config set --local without 'development test mysql'.

Ожидаем: Bundle complete!.

3.7. Инициализация БД
bash
bundle exec rake generate_secret_token
RAILS_ENV=production bundle exec rake db:migrate
RAILS_ENV=production REDMINE_LANG=ru bundle exec rake redmine:load_default_data
Что делают:

generate_secret_token — ключ для сессий

db:migrate — создаёт все таблицы (пользователи, проекты, задачи, статусы)

load_default_data — загружает роли, статусы, трекеры, админа (admin/admin)

3.8. Запуск
Проблема: Rails не находит сервер (Could not find server ""), потому что WEBrick вынесен из стандартной библиотеки Ruby 3.0+.

Решение: добавить puma в Gemfile:

ruby
group :production do
  gem 'puma'
end
Затем:

bash
bundle install
bundle exec rails server -e production -b 0.0.0.0 -p 3000 > /var/log/redmine.log 2>&1 &
Проверка:

bash
curl -I http://localhost:3000
# HTTP/1.1 200 OK

6. Важные выводы для QA
Баг-трекер — обязательный инструмент. Без него баги теряются.

Workflow бага — баг движется по статусам. QA контролирует, что баг дошёл до «Закрыта».
